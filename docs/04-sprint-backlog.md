# 4\. Sprint Backlog — UniLink Hub

## 4.1 Introduction and Sprint Duration

The Sprint Backlog represents the development work selected and organised by the team to move UniLink Hub towards its project objectives.

The team followed a sprint-based development approach. However, the exact sprint duration and formal sprint boundaries are not available. For this reason, the timeline below presents a reconstruction of the project's activities across approximately 12 weeks.

These project phases should not be interpreted as confirmed formal sprints. They provide an overview of how the development work progressed from the initial idea to the final presentation.

## 4.3 My Individual Backend and Database Work Breakdown

My main responsibility during the development process was backend development and database connectivity. The following activities describe the work I was responsible for.

### 4.3.1. Backend Setup and Structure

Worked with Java and Spring Boot to develop the backend structure and supporting functionality.

### 4.3.2. Registration and Security

Worked on account registration and Spring Security configuration, including investigating and troubleshooting authentication and access-related behaviour.

### 4.3.3. API Development

Worked on creating and connecting REST API endpoints to support communication between the frontend and backend.

### 4.3.4. Database Connectivity and Persistence

Worked on testing MySQL database connectivity and checking whether backend operations could interact with the database correctly.

### 4.3.5. Password Protection

Worked on testing password encryption and hashing behaviour to support secure handling of user passwords.

### 4.3.6. API Testing

Used Postman to send API requests, inspect responses and investigate errors during backend development.

### 4.3. 7. Frontend and Backend Integration

Assisted with connecting backend functionality to the frontend and investigating issues that occurred during integration.

These activities helped me understand how individual backend tasks contribute to the overall functionality of a software application.

## 4.5 Personal Reflection

Breaking the development work into different phases helped me understand how a software project progresses from idea discovery and requirements gathering to design, implementation, testing and deployment. During UniLink Hub development, my backend responsibilities involved more than simply writing API endpoint code. I also had to investigate security configuration, test API behaviour, check database connectivity and assist with frontend and backend integration.

One of the main lessons I learned was that different development activities depend on one another. For example, the frontend requires functioning backend endpoints to retrieve and submit information, while the backend requires appropriate database connectivity to store and retrieve application data. I also realised that integration should be tested throughout development rather than being left until the final stages. Identifying integration problems earlier can help reduce delays and make it easier for team members to resolve issues.

Another challenge was managing development activities alongside other project responsibilities. The experience showed me that clear task allocation, regular progress updates and realistic deadlines are important when working towards a shared project goal. In future projects, I would maintain a more structured sprint backlog with clearly defined sprint goals, task owners, acceptance criteria, deadlines and links to supporting evidence. I would also encourage the team to conduct regular progress reviews so that incomplete tasks and technical blockers can be identified earlier.

Although the exact sprint duration and formal sprint boundaries for UniLink Hub are unknown, reconstructing the project timeline helped me reflect on the different development stages and understand the importance of planning, coordination and continuous review in Agile software development.
